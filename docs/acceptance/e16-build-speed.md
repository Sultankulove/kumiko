# Приёмка E16: скорость сборки

Этап E16 (ТЗ v1.1, раздел 9): быстрый линкер, кеш CI, замер до и после.

## Локальная сборка

Замер на Linux (облачный контейнер, 4 vCPU Xeon 2,1 ГГц, debug): после правки в `kumiko-core` пересобрать приложение (`cargo build -p kumiko`) и тесты (`cargo test --no-run --test headless`), по три повтора.

| Линкер | Приложение | Тесты headless |
|---|---|---|
| rust-lld (по умолчанию в Rust ≥ 1.90 на Linux) | 6,7–10,1 с | 3,6–12,2 с (первый прогон — 12,2 с, затем 3,6–3,8 с) |
| mold 2.30 | 6,6–7,2 с | 3,6–3,8 с |

Вывод: на Linux mold не быстрее — Rust уже линкует через rust-lld. mold не добавляется.

На Windows Rust по умолчанию линкует через `link.exe` из MSVC. Теперь `.cargo/config.toml` указывает `rust-lld.exe` для `x86_64-pc-windows-msvc`: он входит в toolchain, ставить ничего не нужно. Если сборка на Windows не находит системные библиотеки, запустить её из «Developer PowerShell for VS» или временно вернуть `link.exe`: `cargo build --config "target.x86_64-pc-windows-msvc.linker='link.exe'"`.

Советы для разработки:

- `cargo check -p <крейт>` вместо полной сборки, когда нужны только ошибки компиляции.
- `cargo test -p <крейт>` вместо `--workspace`.
- Зависимости собираются без отладочной информации (`[profile.dev.package."*"] debug = false`) — так было и раньше.

## CI

До E16 (прогон [39424754476](https://github.com/Sultankulove/kumiko/actions/runs/39424754476), PR в `staging`):

| Задача | Время | Из них |
|---|---|---|
| test (Linux) | 10 мин 20 с | кеш не восстановлен (0 с); `cargo test` 9 мин 11 с: сборка ≈ 5 мин, тесты ≈ 4 мин, из них `the_alt_editor_profile_builds` 2 мин; сохранение кеша 25 с, неудачное («another job may be creating this cache») |
| test (Windows) | 18 мин 49 с | восстановление кеша 1 мин 9 с; `cargo test` 12 мин 3 с; сохранение кеша 4 мин 34 с |
| clippy (Linux / Windows) | 1 мин 14 с / 2 мин 15 с | кеш восстановлен |

Причины:

1. CI запускался на push только в `main`. Этапы теперь сливаются в `staging`, и для PR в `staging` подходящего кеша нет; сам `staging` после слияний не проверялся.
2. Каждый PR сохранял свой кеш: минуты на Windows, а параллельные задачи мешали друг другу.

Изменения:

- CI запускается на push в `main` и `staging`.
- `Swatinem/rust-cache` сохраняет кеш только на push (`save-if`), PR его восстанавливают.
- Windows линкует через rust-lld.

sccache не добавлен: `rust-cache` уже кеширует `target/` целиком, а второй кеш делит с ним лимит GitHub в 10 ГБ на репозиторий. Вернёмся к нему, если после этих изменений холодные сборки останутся частыми.

После E16: замеры добавляются после прогонов на PR и на `staging`.
