# ADR-020. Windows — платформа MVP наравне с Linux

- Статус: Accepted (решение владельца, 26.09.2026)
- Дата: 2026-09-26
- Источник: ТЗ v1.0, раздел 1 (п. 9), разделы 19, 20, 23, 27; дополняет ТЗ

## Контекст

ТЗ ставит первой платформой Linux (x86_64, aarch64), а Windows и macOS относит к дорожной карте после MVP. Владелец работает в основном на Windows и хочет пользоваться IDE там сразу. Архитектура к этому готова: пути идут через один модуль `kumiko-types`, PTY планируется через portable-pty (ConPTY на Windows), ядро, протокол и WASM-плагины от ОС не зависят. От Unix зависят только надзор за процессами (группы процессов, сигналы), часть тестов и сборочные скрипты.

## Решение

1. Платформы первого уровня MVP: **Linux x86_64 и Windows x86_64** (Windows 10 22H2 и новее). Linux aarch64 остаётся целью, macOS — после MVP.
2. Критерии раздела 3 и бюджеты раздела 23 проверяются на обеих платформах. Критерий 15 на Windows — принудительное завершение процесса плагина (`taskkill /F`, `TerminateProcess`) вместо `kill -9`.
3. Критерии UI-спайка (раздел 20) получают пары для Windows:

   | Критерий | Linux | Windows |
   |---|---|---|
   | Оконная система | Wayland и X11 без флагов | Win32, DPI-aware (per-monitor v2) |
   | IME | ibus, fcitx | IME Windows (TSF/IMM32): китайский, японский |
   | Доступность | AT-SPI (AccessKit или эквивалент) | UI Automation (AccessKit или эквивалент) |
   | Графика | Vulkan/GL на встроенной графике | DX12/Vulkan на встроенной графике |

   Тулкит, который не работает на Windows нативно, не проходит спайк.
4. Надзор за процессами на Windows: плагин и его потомки живут в Job Object (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`); вместо SIGTERM → SIGKILL — `shutdown` → `exit` → `TerminateJobObject`. Код, зависящий от ОС, изолируется за `cfg` в одном месте, как сейчас `signal_group`.
5. Пути: `directories` даёт `%APPDATA%\kumiko`, `%LOCALAPPDATA%\kumiko` для данных, кеша и состояния; раздел 22 читается с этой поправкой.
6. Сборочные скрипты плагинов-примеров и тестовые помощники не должны требовать bash: сборка через cargo или маленькие Rust-программы, где нужно.

## План

- Новый этап **E6w. Порт на Windows** сразу после E6 (до UI-хоста E7):
  - CI на `windows-latest` для clippy и тестов;
  - Job Objects в Plugin Host;
  - Windows-варианты тестов, завязанных на `/proc`, `kill` и bash;
  - сборка эталонного C-плагина на Windows (wasi-sdk есть для Windows).
- Начиная с E7 каждый этап принимается на обеих платформах.

## Последствия

- CI удлиняется на задачу Windows; тесты с процессами получают варианты для обеих ОС.
- GTK4 как запасной UI-тулкит практически выбывает: на Windows он требует MSYS2-рантайм и поставку DLL.
- Выбор UI-тулкита учитывает качество Windows-бэкенда. Замеры спайка снимаются нативно на Windows (там есть встроенная графика Intel UHD, как в пороге раздела 20) и на Linux.
