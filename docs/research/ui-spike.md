# UI-спайк (E6): iced, GPUI, GTK4

Этап E6 из ТЗ (раздел 28): прототипы UI-тулкитов и замеры по таблице раздела 20. По итогам принят [ADR-003](../adr/0003-ui-toolkit.md). С учётом [ADR-020](../adr/0020-windows-in-mvp.md) Windows — платформа MVP, поэтому опорные замеры сняты нативно на Windows.

Код: `spikes/ui` (отдельный cargo workspace: зависимости кандидатов не попадают в основную сборку, CI и cargo-deny). Сырые данные: `spikes/ui/results/`.

## Что сделано

Все прототипы получают одинаковую нагрузку из крейта `workload`:
- **файл** на 10 000 строк Java-подобного кода с подсветкой (6 видов токенов);
- **дерево файлов** на 925 узлов с навигацией стрелками;
- **окно** развёрнуто на весь экран.

| Прототип | Редактор | Дерево | Доступность |
|---|---|---|---|
| `iced-proto` (iced 0.14, wgpu) | canvas: видимые строки, по одному текстовому прогону на токен (текст iced — cosmic-text) | `scrollable(column)` | мост AccessKit (`a11y-bridge`) |
| `gpui-proto` (GPUI 0.2.2) | `uniform_list` строк со `StyledText` и подсветкой | `uniform_list` | тот же мост |
| `gtk-proto` (gtk4-rs 0.11, GTK 4.14) | `ListView` строк с разметкой Pango | `ListView` + `SingleSelection` | встроенная (AT-SPI) |

**Режимы замера** (`SPIKE_BENCH`):
- `start` — холодный старт: от момента перед `exec` (`SPIKE_T0`, задаёт скрипт запуска) до первого кадра;
- `scroll` — прокрутка на одну строку за кадр, 600 кадров, интервалы между кадрами;
- `type` — вставка символа каждые 3 кадра, интервалы между кадрами при наборе;
- `probe` — интерактивный режим с маркером, который меняет цвет на каждую нажатую `x`.

**Клавиша → пиксель на Windows** (`latency-probe`): пробник посылает `x` через `SendInput` и опрашивает пиксель маркера на экране через GDI, пока тот не сменит цвет. В замер входит всё: доставка ввода, обновление, раскладка и рендер тулкита, композиция DWM. Не входит только вывод на панель. Один опрос пикселя стоит 6–7 мс, это шаг квантования замера.

**Доступность.** Прототипы iced и GPUI подключают AccessKit снаружи, без форка тулкита:
- **Windows:** `SubclassingAdapter` на HWND окна. Адаптер должен быть создан до первого показа окна, поэтому окно открывается скрытым и показывается после подключения. Оба тулкита это позволяют: у iced это `visible: false`, `window::run` и `set_mode`, у GPUI — `show: false` и `activate_window`.
- **Linux:** `accesskit_unix`, дескриптор окна не нужен.

Проверка — `scripts/uia-check.ps1`, клиент UI Automation (так видят окно экранные чтецы): ищет дерево, считает элементы, нажимает ↓↓↓ и читает, где фокус.

**Воспроизведение:**
- Windows: `spikes/ui/scripts/run-windows.ps1`, плюс `start-variants.ps1` и `start-breakdown.ps1` для разбора старта iced;
- Linux: `cargo build --release -p <прототип>` и запуск с `SPIKE_BENCH`.

## Результаты: Windows (опорные)

Ноутбук: Windows 11, экран 1920×1200 при масштабе 125%, 165 Гц. Изображение выводит встроенная Intel UHD Graphics (в системе есть и RTX 4060, адаптер по умолчанию). Release-сборки.

| Критерий раздела 20 | Порог | iced 0.14 | GPUI 0.2.2 |
|---|---|---|---|
| Прокрутка 10 000 строк с подсветкой | ≥ 60 fps | **162 fps** (кадр p95 6,9 мс) ✅ | **160 fps** (p95 6,6 мс) ✅ |
| Кадры при наборе | — | 162 fps (p95 6,8 мс) | 164 fps (p95 6,6 мс) |
| Клавиша → пиксель, с DWM и шагом опроса ~6 мс | p95 < 16 мс | p50 22,6, p95 29,0, max 61 мс | p50 12,6, p95 24,2, max 26 мс |
| Холодный старт окна | < 300 мс | **1,5–2,4 с** ❌; первый запуск 8,4 с | **~190 мс** ✅; первый запуск 760 мс |
| RAM в покое, через 30 с (бюджет раздела 23: < 120 МБ) | < 120 МБ | 242 МБ рабочий набор, 307 МБ private ❌ | 89 МБ рабочий набор, 127 МБ private ✅ |
| Доступность (UI Automation) | AccessKit или эквивалент | ✅ дерево, 925 элементов, фокус на выбранном `TreeItem` | ✅ то же |
| IME | работает в редакторе | API есть: `InputMethod` в виджетах, winit → IMM32 | API есть: `EntityInputHandler`, `WM_IME_COMPOSITION`; на нём работает редактор Zed |
| Win32, per-monitor DPI | без флагов | ✅ | ✅ |

**Холодный старт iced.** Время уходит в инициализацию wgpu, а не в интерфейс:

| Вариант | Холодный старт, мс |
|---|---|
| По умолчанию | 2173–2386 |
| `WGPU_BACKEND=dx12` | 1618–1944 |
| `WGPU_BACKEND=vulkan` | 1493–1560 |
| `dx12` + `WGPU_POWER_PREF=low` / `high` | 1492–2007 / 1654–1717 |
| Без AccessKit (окно сразу видимо) | 1826–2967 |
| Только редактор, без дерева | 1673–1859 |
| Пустой canvas | 1990–2293 |
| Программный рендер tiny-skia | 329–356 (но прокрутка 18 fps) |

Шрифты ни при чём (`font-probe`): cosmic-text грузит 605 системных шрифтов Windows за 32–52 мс, а базу из одного моноширинного шрифта — за 0,1 мс.

**Клавиша → пиксель.** Ни один тулкит не прошёл порог 16 мс по этому замеру, но он даёт верхнюю оценку:
- кадр композиции DWM при 165 Гц — это 6 мс;
- шаг опроса пикселя — ещё около 6 мс.

У GPUI медиана 12,6 мс, то есть половина нажатий видна меньше чем за 2 кадра экрана. Точный замер без DWM и опроса (фотодатчик или захват с таймстемпами кадров) — задача для приёмки бюджетов в E8 и E14.

## Результаты: Linux (WSLg, ориентировочные)

В WSLg графика идёт через D3D12-прослойку, Vulkan-драйвера для GPU нет, поэтому рисование программное (lavapipe или llvmpipe). Цифры годятся только для сравнения кандидатов между собой.

| | iced | GPUI | GTK4 |
|---|---|---|---|
| X11: холодный старт | 110–140 мс | 70–80 мс | 190–230 мс |
| X11: прокрутка | 60–74 fps, но отдельные прогоны зависают в EGL/zink | 52–60 fps (упор в 60 Гц) | 24 fps |
| Wayland (Weston WSLg): старт / прокрутка | 135–175 мс / 14–19 fps | **падает на старте**: `unwrap()` на `UnsupportedVersion` протокола композитора | 280–330 мс / 24 fps |
| RSS | 230–255 МБ | 130–190 МБ | 176–247 МБ |

Wayland и X11 на нативном Linux (GNOME или KDE, встроенная графика) нужно перемерить: это условие ADR-003.

## Прочие находки

- **GPUI 0.2.2 на Linux:**
  - под Wayland WSLg (старый Weston) падает на старте вместо деградации;
  - `window_handle()` окна X11 — `unimplemented!()`, в прототипе обойдено: AccessKit на Linux дескриптор не нужен.

  Оба места — кандидаты на патч, если на нативных композиторах воспроизведутся.
- **GPUI на Windows** рисует через DirectX, а текст шейпит через DirectWrite. cosmic-text используется только на Linux.
- **iced** рисует текст через cosmic-text на всех ОС. Но это не выигрыш сам по себе: старт и память под Windows не проходят пороги.
- **iced 0.14 перерисовывает кадр** только при видимом изменении. Для анимаций и замеров нужен визуальный «тик».
- **GPUI перерисовывает вид** только после `cx.notify()`. Список `uniform_list` строит строки при раскладке, иногда дважды за кадр.
- **GTK4 выбывает:** на Windows нужен MSYS2-рантайм (ADR-020), а прокрутка в WSLg самая медленная, хотя доступность встроена.
- **Лицензии** обоих деревьев совместимы с Apache-2.0:
  - iced — 329 крейтов, GPUI — 675;
  - из не MIT/Apache только `self_cell` (Apache-2.0 OR GPL-2.0, берём Apache) и `option-ext` (MPL-2.0, уже есть в проекте через `directories`).
- **Сборка на Windows:** в переменных пользователя задано `CC=clang` без установленного clang. Для сборки `ring` (зависимость GPUI) переменную снимаем в процессе сборки.

## Итог

GPUI проходит все измеренные пороги, кроме «клавиша → пиксель»: его точный замер отложен, а по верхней оценке GPUI лучше iced. У iced не проходят холодный старт и память на Windows. Условия принятия GPUI и последствия — в [ADR-003](../adr/0003-ui-toolkit.md).
