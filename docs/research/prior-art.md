# Прецеденты и уроки

Заметка Phase 0 (ТЗ, раздел 7). Для каждого проекта: что берём, чего избегаем и как это отражено в решениях Kumiko. Пункты с пометкой **проверить** — утверждения, которые нужно подтвердить по первоисточнику до того, как на них опирается решение (обычно в спайке или на соответствующем этапе).

Дата: 23.09.2026.

## VS Code

**Модель.** Расширения описывают вклады декларативно в `package.json` (`contributes`: команды, меню, keybindings, настройки, языки, views). Код расширения загружается лениво по activation events (`onLanguage`, `onCommand`, `workspaceContains`). Видимость и доступность элементов меню и клавиш управляются when-clause contexts, которые вычисляет хост, не опрашивая расширения. Все расширения окна живут в общем Extension Host (Node.js-процесс). LSP и DAP появились именно здесь и стали отраслевыми стандартами.

**Берём.**
- Декларативные вклады в манифесте и ленивую активацию → раздел 13, `[[contributes.*]]`, `activation`.
- Context keys и when-выражения, вычисляемые ядром → раздел 11, проблема P6.
- LSP и DAP как Language API и Debugger API → ADR-005, ADR-006.

**Избегаем.**
- Общий хост для всех расширений: одно медленное расширение задерживает остальные, а память хоста растёт вместе с числом расширений. В Kumiko по умолчанию WASM in-process с лимитами на плагин, процессы — поштучно (P17); общие рантайм-хосты — только после MVP и отдельным ADR-017.
- Webview как универсальный UI API: он обходит тему, доступность и бюджет памяти. В MVP только декларативные UI-модели (раздел 20), решение о будущем — open-question-4.

## Zed

**Модель.** Rust, собственный GPU-тулкит GPUI. Расширения — git-репозитории с `extension.toml`; декларативная часть (языки, темы, иконочные темы, сниппеты) не требует кода, процедурная пишется на Rust и компилируется в WASM-компонент (`wasm32-wasip2`). WIT-мир версионируется каталогами `since_vX.Y.Z`, хост поддерживает несколько версий одновременно.

Что даёт их WIT (по `extension_api/wit/since_v0.6.0/extension.wit`):
- экспорты: команда запуска языкового сервера, его initialization options и workspace configuration, подписи элементов completion и символов, slash-команды ассистента, context servers (MCP), debug adapters, индексация документации;
- импорты: загрузка файлов, чтение файлов worktree, `which`, окружение shell, настройки, key-value хранилище, статус установки языкового сервера.

Чего нет: собственных панелей и деревьев, команд палитры и меню, правки документов, подписки на события редактора. Расширение Zed — «интегратор инструмента», а не плагин редактора.

**Берём.**
- WASM Component Model + WIT как стабильный ABI для плагинов на любом языке → ADR-010.
- Декларативные расширения без кода → пакеты L3, `kind = "data"` (раздел 21).
- Версионирование WIT по каталогам с поддержкой нескольких мажорных версий в хосте → применить к `sdk/wit/kumiko-plugin/` при первом мажорном изменении KPP.
- Язык плагина запускает языковой сервер, а ядро владеет LSP-клиентом → `lsp/resolveLaunch` (раздел 18).

**Избегаем.**
- Узкого API, который не позволяет плагину делать UI и работать с документами: это главный ограничитель экосистемы. У Kumiko в KPP есть `command/`, `document/`, `ui/` (декларативные модели), `service/` (межплагинные интерфейсы).

**Проверить.** Лицензию крейта `gpui` и стабильность его API вне репозитория Zed (кандидат спайка ADR-003). Как Zed загружает грамматики Tree-sitter (WASM через wasmtime) — вход для пересмотра ADR-011.

## Lapce

**Модель.** Rust, тулкит Floem (реактивный, рендер через wgpu), плагины («volts») — WASI-модули на языках с компиляцией в WASI (Rust, C, AssemblyScript). Отдельный proxy-процесс (`lapce-proxy`) выполняет работу с ФС, LSP и плагинами — это же основа удалённой разработки.

**Берём.**
- Подтверждение, что Rust-тулкит с wgpu способен нести редактор; Floem — референс для спайка (ADR-003), хотя не кандидат.
- Идею, что плагины и LSP живут вне UI-потока.

**Избегаем / изучить.**
- Плагинный API, фактически сведённый к запуску LSP-серверов и настройкам: плагину почти нечего делать, кроме как быть лаунчером сервера. **Проверить** по текущему API volts, какие ещё возможности (UI, команды) добавлены.
- Разделение UI и «ядра» на процессы с самого начала: для локальной IDE это цена без выигрыша (см. xi-editor). В Kumiko ядро и UI в одном процессе, удалённый UI — после MVP поверх KPP.
- **Проверить**: как решены терминал (PTY в proxy) и темп разработки проекта в 2025–2026 — это индикатор стоимости сопровождения собственного тулкита.

## Helix

**Модель.** Модальный редактор на Rust. Языки описываются `languages.toml`; грамматики Tree-sitter собираются командой `hx --grammar fetch/build`; queries лежат в `runtime/queries/<lang>/` (`highlights.scm`, `injections.scm`, `textobjects.scm`, `indents.scm`, `locals.scm`). Плагинной системы в релизах долго не было; встраиваемый язык расширений (Steel, диалект Scheme) развивается отдельно много лет.

**Берём.**
- Раскладку queries по типам и runtime-каталог грамматик → пакет грамматики L3 (раздел 18): `grammar.toml` + парсер + `queries/{highlights,folds,locals,textobjects,indents}.scm`.
- Набор capture-имён highlights как основу маппинга на токены темы (раздел 21).

**Избегаем.**
- Добавления расширяемости «потом»: когда внутренние структуры уже сложились без границ, API для плагинов приходится вырезать из монолита годами. В Kumiko протокол, манифест и архитектурный тест появляются с E0–E1, до функциональности.

## xi-editor

**Модель.** Ядро на Rust с rope-буфером и CRDT для правок, frontend в отдельном процессе, связь JSON-RPC, асинхронная модель «всё — сообщение». Проект заморожен; автор опубликовал ретроспективу (Raph Levien, «xi-editor retrospective», 2020).

**Берём.**
- Rope как структуру буфера (в Kumiko — ropey, иммутабельные снимки).
- Версии документа и ремаппинг устаревших результатов через список правок (раздел 12).

**Избегаем.**
- Асинхронного разделения UI и ядра на процессы: оно превращает простые синхронные операции (ввод символа, выделение, прокрутку) в распределённую систему с гонками → P15: UI в процессе ядра, связь типизированными каналами.
- CRDT без сценария совместного редактирования: сложность без пользы для MVP. У Kumiko линейная история версий, ребейз правок и `ContentModified` при конфликте.

## IntelliJ IDEA

**Модель.** Монолитная платформа на JVM с собственным анализатором (PSI), индексами и моделью проекта; плагины — JAR-ы в том же процессе с доступом ко внутреннему API.

**Берём.**
- Эргономику Java-сценариев: run configurations, запуск тестов из редактора, выбор JDK на уровне проекта, организация импортов → задачи Maven, `java.selectJdk`, quick fixes (раздел 18).

**Избегаем.**
- Собственного анализатора и модели зависимостей (вне цели, раздел 4): аналитика — от JDT LS, модель проекта — от build-плагина (P10).
- In-process плагинов с доступом ко всему внутреннему API: любой плагин может сломать или замедлить IDE, а совместимость между версиями держится на неформальных договорённостях. В Kumiko L2 изолированы стабильным версионированным KPP.

## Выводы для Kumiko

| Урок | Где отражено |
|---|---|
| Декларативные вклады + ленивая активация + when-выражения | Разделы 11, 13 |
| WIT как ABI плагинов, версионирование WIT по каталогам | ADR-010; применить в `sdk/wit/` |
| Узкий плагинный API душит экосистему | KPP: команды, документы, UI-модели, интерфейсы |
| Общий хост расширений плохо изолирует | WASM на плагин с лимитами; ADR-017 после MVP |
| Асинхронное разделение UI/ядра дорого | P15, ADR-001 |
| Расширяемость нельзя добавить поздно | Протокол и архитектурный тест с E0–E1 |
| Грамматики и queries — данные L3 | Раздел 18, ADR-011 |
