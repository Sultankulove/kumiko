Как переносить:
- **MIT и Apache-2.0** — код можно переносить. В шапке файла указывается источник («Adapted from …»), лицензия сохраняется в `NOTICE`.
- **MPL-2.0 (Helix)** — предпочитаем переписать идею своим кодом. Если файл переносится как есть, он остаётся под MPL-2.0 с исходной шапкой и лежит отдельно (cargo-deny MPL разрешает).

## Выводы по темам

### 1. Модель правок

**У Helix:**
- правка — `ChangeSet` из операций `Retain(n)`, `Delete(n)`, `Insert(text)` по символам всего документа;
- умеет `compose` (склейка правок), `invert` (для undo) и `map_pos` с привязкой `Assoc` (куда «прилипает» позиция при вставке рядом);
- `Transaction` = `ChangeSet` + выделение после правки.

**У нас:** список `TextEdit` (строка и UTF-8 колонка). Это формат протокола KPP и LSP, его оставляем.

**Берём идею:** внутри редактора нужен перенос позиций через правку. Курсоры всех view документа, метки, предредактирование и декорации должны правильно сдвигаться, когда правит другой view, плагин или внешнее изменение файла. Делаем функцию «отобразить позицию через набор `TextEdit`» с привязкой «до/после». Это небольшой и хорошо тестируемый модуль.

**Undo:**
- в Helix дерево ревизий с метками времени, переходы «раньше/позже»;
- наш линейный undo с группами по времени для MVP достаточен;
- дерево — после MVP, если понадобится.

**Не хватает:** undo должен восстанавливать выделения. Helix хранит выделение вместе с транзакцией. Добавим выделение до и после правки в группу undo.

### 2. Выделения и мультикурсоры

**У Helix:**
- `Range { anchor, head }` в «промежутках» между символами: голова двигается, якорь стоит;
- `Selection` — список диапазонов с главным, после каждой операции нормализуется (пересекающиеся сливаются);
- выделения хранятся в документе отдельно для каждого view (`HashMap<ViewId, Selection>`). У нас это сразу состояние view (ТЗ, раздел 12: «курсоры — состояние view»), что ещё проще.

**Берём идею целиком, пишем своё:** `Range`, `Selection`, нормализация, отображение через правки. Позиции — смещения в символах rope. В `TextEdit` и протокол переводятся на границе.

**У Floem** курсор помнит «желаемую колонку» для движения вверх/вниз (`horiz`). Это тот же механизм, что `old_visual_position` у Helix. Нужно обязательно, иначе курсор «съезжает» на коротких строках.

### 3. Движение и графемы

- Влево/вправо — по графемам, а не по символам: эмодзи, комбинирующие знаки, `\r\n` как одна позиция. В Helix это `graphemes.rs` поверх `unicode-segmentation` (MIT/Apache): небольшие функции, перепишем.
- Слова — классы символов: слово, пробел, пунктуация, перевод строки. Возьмём `word.rs` из Floem (MIT) с указанием источника, он не зависит от xi-rope.
- `Home` как в IntelliJ: первое нажатие — к первому непробельному символу, второе — к началу строки. `PageUp/PageDown`, `Ctrl+Home/End` — тривиально.

### 4. Отрисовка и IME (главный риск E8)

**Образец — пример `input.rs` из самого GPUI** (Apache-2.0, наш тулкит):
- элемент регистрирует `window.handle_input(…, ElementInputHandler::new(bounds, entity))`;
- view реализует `EntityInputHandler`:
  - `replace_text_in_range` — обычный ввод;
  - `replace_and_mark_text_in_range` — предредактирование IME;
  - `marked_text_range` и `unmark_text`;
  - `bounds_for_range` — где показать окно кандидатов IME;
  - `character_index_for_point` — попадание мышью.
- Через этот же механизм GPUI подключает IME Windows (TSF/IMM) и ibus/fcitx на Linux. Это закрывает условие ADR-003 про IME без своего кода под каждую ОС.
- **Единицы — UTF-16** (`UTF16Selection`, диапазоны в UTF-16). Нужен перевод UTF-16 ↔ символы rope на границе обработчика.

**Предредактирование:**
- у Floem набираемый, но не подтверждённый текст рисуется как фантомный текст в документе;
- у нас он живёт **в состоянии view**, а не в документе: не создаёт правок, версий, undo и событий для LSP. В документ попадает только подтверждённый текст.

**Отрисовка строк:**
- рисуем только видимые строки: `uniform_list`, как в спайке и в текущем просмотре файлов;
- каждая строка — `window.text_system().shape_line(...)` с запусками стилей из подсветки;
- кеш раскладки по номеру строки и версии документа;
- позиция курсора по X — `ShapedLine::x_for_index`, попадание мышью — `index_for_x`.

**Перенос строк:** у Floem `visual_line.rs` — 3,5 тысячи строк сложного кода. В списке функций MVP (ТЗ, раздел 12) переноса нет, в E8 его не делаем.

### 5. Синхронизация с LSP (на E9)

У Helix `changeset_to_changes` превращает правку в инкрементальные `contentChanges`, `pos_to_lsp_pos` и `lsp_pos_to_pos` учитывают кодировку (UTF-8/16/32). У нас `TextEdit` уже в формате LSP с UTF-8, так что сервер с `positionEncoding: utf-8` получает правки как есть. Для UTF-16 нужен такой же перевод, как для IME, — общая функция в `kumiko-types`.

Lapce держит LSP в proxy-процессе со своим протоколом (PSP). У нас LSP-клиент живёт в ядре (ТЗ, раздел 18), эта часть не переносится.

## План E8, следующий из разбора

1. **Модель редактора** (`kumiko-editor-view`, без GPUI, с тестами):
   - `Range`, `Selection`, нормализация, перенос через правки;
   - движение по графемам, словам, строкам, страницам с «желаемой колонкой»;
   - команды редактирования: ввод, Backspace/Delete, Enter с копированием отступа, Tab, удаление строки, дублирование;
   - мультикурсоры как в IntelliJ: `Alt+Shift+клик`, клон каретки вверх и вниз, `Alt+J` — следующее вхождение;
   - буфер обмена с распределением по курсорам; undo и redo через `DocumentService` с восстановлением выделений.
2. **Элемент GPUI:**
   - видимые строки, каретка с миганием, выделения;
   - мышь: клик, протяжка, двойной клик — слово, `Shift`-клик;
   - IME по образцу `input.rs`; прокрутка.
3. **Поиск и замена в файле** (с регулярными выражениями) — панель над редактором, как в IntelliJ.
4. **Tree-sitter Java:** подсветка и сворачивание через `kumiko-syntax`, грамматика — ресурс L3 (ТЗ, раздел 18).
5. **Замеры бюджетов раздела 23** для открытия файла и ввода, ручная проверка IME (условие ADR-003), критерии MVP 4–6.
