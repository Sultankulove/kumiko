# Kumiko Plugin Protocol (KPP)

Версия протокола: **0.1.0** (статус 0.x до заморозки v1 на этапе E14, ТЗ, раздел 16). Документ описывает линию v1; при заморозке версия станет 1.0.0.

Нормативные источники, которые проверяются тестами на совпадение с кодом `kumiko-protocol`:

| Артефакт | Путь |
|---|---|
| Типы и каталог методов | `crates/kumiko-protocol` |
| JSON Schema (draft 2020-12) всех payload-ов | [`sdk/schema/kpp.schema.json`](../../sdk/schema/kpp.schema.json) |
| WIT-пакет для WASM-плагинов | [`sdk/wit/kumiko-plugin/`](../../sdk/wit/kumiko-plugin/plugin.wit) |

Любое изменение протокола сопровождается обновлением всех четырёх (ТЗ, раздел 30, правило 3). Схема и таблицы ниже генерируются: `KUMIKO_BLESS=1 cargo test -p kumiko-protocol --test artifacts`.

## 1. Модель

Один каталог методов обслуживает оба вида плагинов:

- **процессные** — JSON-RPC 2.0 в бинарных фреймах поверх stdin/stdout; stderr плагина идёт в лог ядра;
- **WASM** — WIT-мир `kumiko-plugin`: те же методы, params и результаты — JSON-строки той же схемы.

H — host (ядро), P — plugin. У каждого метода фиксировано направление: H→P, P→H или оба.

## 2. Транспорт процессных плагинов

Фрейм (реализация — `kumiko-ipc`, этап E2):

| Поле | Размер | Значение |
|---|---|---|
| length | u32 LE | Длина остатка фрейма, максимум 16 МБ |
| kind | u8 | 0 — JSON-RPC (UTF-8 JSON), 1 — данные потока, 2 — закрытие потока |
| stream_id | u32 LE | Только для kind 1 и 2 |
| payload | остаток | JSON или сырые байты |

Идентификаторы потоков (`StreamId`) выдаёт сторона, открывающая поток, в ответе на запрос (например, `process/spawn` возвращает `stdout` и `stderr`).

## 3. Привязка к WASM

Пакет `kumiko:plugin@0.1.0`, мир `kumiko-plugin`:

| Интерфейс | Направление | Функции |
|---|---|---|
| `host` (импорт) | P→H | `call(method, params) -> result<string, rpc-error>`, `notify(method, params)`, `stream-write(id, data)`, `stream-close(id)` |
| `plugin` (экспорт) | H→P | `handle(method, params) -> result<string, rpc-error>`, `on-notify(method, params)`, `on-stream(id, data)`, `on-stream-close(id)` |

`rpc-error { code: s32, message: string, data: option<string> }` — тот же объект ошибки, что в JSON-RPC; `data` — JSON-строка. Отмена (`$/cancelRequest`) и прогресс идут через `notify`/`on-notify`, как у процессных плагинов.

## 4. Конверт JSON-RPC 2.0

- Запрос: `{"jsonrpc": "2.0", "id": <number|string>, "method": "...", "params": {...}}`.
- Уведомление: без `id`.
- Ответ: `{"jsonrpc": "2.0", "id": ..., "result": ...}` или `{"jsonrpc": "2.0", "id": ..., "error": {"code", "message", "data"?}}`; `id: null` — только если id запроса не удалось прочитать.
- Метод без параметров отправляется без `params`; метод без результата возвращает `null`.
- Батчи JSON-RPC не используются.

## 5. Соглашения о payload-ах

- Имена полей — camelCase.
- Необязательные поля можно опустить или передать `null`; неизвестные поля игнорируются.
- Позиции — `{line, character}`, где `character` — байт UTF-8 внутри строки (ADR-012). Диапазоны полуоткрытые `[start, end)`.
- URI — строки с обязательной схемой; ядро интерпретирует только `file:`.
- Бинарные данные в JSON — `{"text": "..."}` для UTF-8 или `{"base64": "..."}`; большие объёмы идут потоками, а не JSON.
- Иконки и цвета в UI-моделях — токены темы, не значения.

## 6. Handshake и жизненный цикл

1. H→P `initialize {apiVersion, pluginId, hostCapabilities, workspace, config, locale}`.
2. P→H ответ `{apiVersion, pluginCapabilities}`. Разные мажорные версии → ошибка `ApiVersionMismatch`, плагин не запускается. Мажорная версия проверяется ещё до запуска по полю `api` манифеста.
3. H→P `initialized`. Дальше запросы идут в обе стороны.
4. Остановка: H→P `shutdown` (3 с) → `exit` → SIGTERM (2 с) → SIGKILL.

**Capabilities.** Минорные версии добавляют методы. Вместо сравнения версий стороны объявляют, что умеют:

- `hostCapabilities.methods` — P→H методы, которые реализует ядро;
- `pluginCapabilities.methods` — необязательные H→P методы, которые обрабатывает плагин (`state/save`, `state/restore`, `document/resolveContent`, `task/provide`, `task/resolve`, `ui/tree/getChildren`, `lsp/resolveLaunch`, `service/invoke`…);
- `pluginCapabilities.lspMiddleware` — методы LSP, которые плагин перехватывает.

Неизвестный метод получает `MethodNotFound`.

## 7. Правила

- **Отмена.** Любой запрос отменяется `$/cancelRequest {id}`; ответ — ошибка `RequestCancelled`.
- **Таймауты.** 5 с для H→P; 1 с на горячем пути (completion, hover): опоздавший ответ отбрасывается. Первый вызов плагина ждёт `initialized` до 10 с (процесс) или 2 с (WASM).
- **Backpressure.** Очередь соединения ограничена 1024 сообщениями. События класса B склеиваются или отбрасываются со счётчиком, класса A — подписка сбрасывается и отправляется `$/resync`, запросы получают `Overloaded`.
- **Реализация в ядре (`kumiko-ipc`).** Входящие запросы обрабатываются параллельно, не более 1024 одновременно; сверх лимита сразу приходит `Overloaded`. Исходящие запросы и уведомления ждут места в очереди, потерять событие можно только через неблокирующую отправку. Ответы и `$/cancelRequest` идут вне очереди, поэтому ответ может обогнать уведомления, отправленные его обработчиком раньше. Уведомления обрабатываются строго в порядке прихода. `$/ping` отвечает сам транспорт. Медленный потребитель бинарного потока тормозит чтение всего соединения — это и есть backpressure для потоков.
- **Namespace.** Плагин публикует события, выставляет context keys и меняет настройки только в своём namespace (`<ns>.*`); иначе — `PermissionDenied`.
- **Permissions.** Для WASM-плагинов вызов без нужного разрешения возвращает `PermissionDenied`: `fs/*` требует `fs.workspace`, `process/*` — `process.spawn`, `ui/*` — `ui`. Для процессных плагинов разрешения в MVP декларативны.

## 8. События

Подписка — `event/subscribe {topics, glob?}`; доставка — `event/notify {subscription, topic, payload}`. `topics` принимает точные имена и префиксы вида `document.*`.

- **Класс A** (состояние) — без потерь, порядок в пределах источника. Событие документа несёт версию, и версии идут подряд. При переполнении очереди ядро отменяет подписку и шлёт `$/resync {topics}`: плагин перечитывает состояние (`document/snapshot`) и подписывается заново. То же обязан сделать плагин, заметивший разрыв версий.
- **Класс B** (уведомления) — at-most-once с coalescing; `fs.changed` агрегируется окном 50–100 мс.

## 9. Документы

Документ принадлежит ядру (ADR-004). `document/applyEdit {uri, baseVersion, edits}` применяет правки одной транзакцией. Если `baseVersion` устарела, ядро ребейзит правки через накопленные изменения; при конфликте возвращается `ContentModified`. Документы в собственных URI-схемах плагина (read-only) ядро открывает само, а содержимое запрашивает у плагина через `document/resolveContent`.

## 10. Межплагинные интерфейсы

P→H `service/call {interface, method, params}` ядро маршрутизирует провайдеру как H→P `service/invoke {…, caller}` и при необходимости активирует его (`onInterface:<id>`). Отсутствует опциональный интерфейс → `NotFound`; нет провайдера подходящей версии → `InterfaceVersionMismatch` (ТЗ, раздел 14).

## 11. Отличия от эскиза каталога в ТЗ

Каталог ТЗ (раздел 16) — эскиз. Реализация добавляет методы, без которых описанные в ТЗ функции невозможны:

| Метод | Почему |
|---|---|
| `ui/tree/getChildren` (H→P) | TreeView с «ленивыми детьми» (раздел 20) требует запроса детей у плагина |
| `ui/progress/cancel` (H→P) | Прогресс с отменой (раздел 20) требует сообщить плагину об отмене |
| `process/exited` (H→P) | Процессы плагина должны сообщать код завершения (`wait` у Process Service, раздел 11) |
| `on-stream-close` в WIT | Аналог фрейма kind 2 для WASM-плагинов |

Ещё одно уточнение: методы жизненного цикла (`initialize`, `initialized`, `shutdown`, `exit`) идут без префикса, как в LSP и на диаграмме handshake в ТЗ; `state/save` и `state/restore` относятся к тому же пространству.
