## 1. Цель после MVP

Kumiko — **лёгкая native IDE для Java на Rust**, замена IntelliJ IDEA для повседневной backend-разработки: Spring Boot, JPA/Hibernate, SQL/PostgreSQL, Redis, Kafka, RabbitMQ, gRPC, REST, отладка, переменные окружения. Отличия от IDEA:

- **Лёгкость.** Сама IDE укладывается в бюджеты раздела 23 v1.0 и раздела 10 этого документа. Тяжёлый анализ идёт во внешних серверах (JDT LS, Spring Boot LS), которые можно выключить.
- **Свободная лицензия.** Apache-2.0 (ADR-009), без платных редакций.
- **Горячая замена.** Любой компонент — редактор, Java-сервер, Git, терминал и прочие — заменяется без пересборки. Плагины — прямо в работающей IDE, компоненты L1 — мягким перезапуском без потери сессии (раздел 4).
- **Красота и настраиваемость.** Внешний вид уровня IntelliJ New UI, окно настроек с поиском, свои темы, шрифты, раскладка панелей и клавиш (раздел 6).

Пункт 9 раздела 1 v1.0 уже заменён ADR-020 (Linux и Windows). macOS остаётся после E25.

## 3. Изменения в ТЗ v1.0

### 3.1. Раздел 4 «Что НЕ делать»

Снимаются запреты (реализуются в этапах этого документа):

- полноценный debugger → E19;
- Database-плагин: SQL-редактор, схема, выполнение запросов (собственный database engine по-прежнему запрещён) → E22.

Остаются в силе: собственный Java-компилятор, Git, terminal emulator, LLM; marketplace и онлайн-registry; синхронизация настроек; cloud IDE; webview и произвольный рендер из плагинов; sandbox процессных плагинов; общие рантайм-хосты; macOS; удалённые ФС; multi-root в UI.

### 3.2. Раздел 27 «Дорожная карта»

Фазы «Debugger», «Database-плагин» и «Hot reload» переносятся в этапы E19, E22 и E25. Остальное остаётся в дорожной карте после E25, порядок решит владелец. В неё добавляется фаза «Горячая замена L1 внутри процесса» (ADR-018).

### 3.4. Раздел 28 «План реализации»

Таблица дополняется этапами E15–E25 (раздел 9). Правила раздела 30 v1.0 сохраняются. Добавляются:

13. Этап делается в ветке `eNN-<имя>` от `staging`; PR в `staging`; агент сливает его сам, когда CI зелёный.
14. Релизный PR `staging` → `main` открывается в конце этапа, которым завершается релиз (раздел 7). Агент сливает его, когда CI зелёный и чек-лист релиза выполнен. Тег ставится на `main`.

16. Каждый этап, затрагивающий UI, прикладывает к PR скриншоты в тёмной и светлой темах.

## 4. Горячая замена компонентов

Цель: ни одна замена компонента не требует пересборки IDE, и ни одна не теряет работу пользователя.

### 4.1. Плагины (L2) и ресурсы (L3) — на лету

Это уже работает: установка, удаление, включение и выключение без перезапуска. В E25 добавляются:

- **Обновление версии на лету**: `state/save` у старого экземпляра → остановка → запуск новой версии → `state/restore`. Методы уже есть в KPP v1 (`docs/protocol/v1.md`); хост начинает их вызывать.
- **Замена реализации интерфейса** (ADR-014): например, другой Git-плагин вместо `kumiko.git`. Потребители интерфейса переподключаются без перезапуска, открытые view перерисовываются.
- **Замена языкового сервера**: например, другой Java-сервер вместо JDT LS. Документы переоткрываются у нового сервера, диагностика восстанавливается.
- **Ресурсы L3** (темы, грамматики, иконки, keymap, локали) применяются сразу после смены.
- **Режим разработки плагина**: watcher на папку плагина, пересборка и перезагрузка при сохранении (`kumiko plugin dev <папка>`).

### 4.2. Компоненты L1 — мягкий перезапуск

Редактор, workbench, дерево файлов и view терминала собираются как сейчас (профили сборки, ADR-013). Новое:

- **Дистрибутив со сменными L1.** Альтернативная реализация L1 поставляется как отдельный бинарь UI того же дистрибутива; выбор делается настройкой `workbench.components.<слот>` или через kit.
- **Мягкий перезапуск.** При смене L1 IDE сохраняет сессию и перезапускается, затем восстанавливает: окна, layout, вкладки, курсоры, выделения, прокрутку, несохранённые правки (из backup, раздел 23 v1.0), историю undo открытых файлов, терминальные сессии (процессы shell живут в отдельном процессе-хозяине PTY, view переподключается со scrollback), запущенные задачи и сеансы отладки (переподключение к адаптеру). Цель — меньше 1,5 с.
- **Вынос из L1.** В E25 составляется список того, что можно перенести из L1 в плагины через модели UI раздела 6.3 и v1.0 раздела 20, и переносится то, что не нарушает бюджеты. Кандидаты: Problems, Output, окно Commit, будущие окна Database и HTTP.

### 4.3. Горячая замена L1 внутри процесса — позже

Это отдельная фаза дорожной карты после E25: стабильная граница L1 (C ABI или WASM-компоненты с доступом к рендеру, ADR-018). Чтобы её можно было добавить без переделки, публичные сигнатуры трейтов L1 не должны содержать типы GPUI (проверить в E25 и поправить, где это не так).

## 5. Java-экосистема: состав и источники

Принцип раздела 1 v1.0 сохраняется: протоколы заимствуются. Серверы анализа — существующие открытые (отдельные процессы, их лицензии не распространяются на Kumiko). Своё пишется только там, где готового нет.

| Область | Что получает пользователь | На чём строится | Этап |
|---|---|---|---|
| Java (доделки) | Переход в классы JDK и библиотек (`jdt://`, read-only документ), выбор JDK из списка в строке статуса, Gradle-импорт | JDT LS (EPL-2.0): Gradle импортирует встроенный Buildship; Gradle Tooling API (Apache-2.0) — для задач | E18 |
| Debug | Точки останова (условные, logpoints), шаги, стек, переменные, watch, evaluate, hot code replace, отладка тестов и Spring Boot | DAP-клиент в ядре (ADR-006); адаптер java-debug (EPL-1.0) как бандл JDT LS; поведение — по vscode-java-debug (MIT) | E19 |
| Запуск и env | Конфигурации запуска (main-класс, тест, Maven/Gradle-цель, Spring Boot), переменные окружения, файлы `.env`, профили Spring, VM-опции, compound-запуск | Свой формат `.kumiko/launch.toml`; поля — по образцу run configurations IntelliJ Community (Apache-2.0) и `launch.json` VS Code | E20 |
| Spring / Spring Boot | Навигация по бинам, `@Autowired`→реализация, автодополнение и проверка `application.properties`/`.yml`, список эндпоинтов, live-данные запущенного приложения через Actuator, проверка `@Query` | Spring Boot Language Server из Spring Tools (EPL-1.0) как языковой сервер плагина | E21 |
| SQL / PostgreSQL | Подключения, SQL-редактор с автодополнением по схеме, выполнение запросов, таблица результатов, просмотр схемы, экспорт CSV/JSON | Драйверы — Rust (`tokio-postgres`, `sqlx`: MIT/Apache-2.0); автодополнение — postgres-language-server (MIT) или sqls (MIT); UI — по образцу DBeaver (Apache-2.0) | E22 |
| JPA / Hibernate | Проверка `@Entity`/`@Column` против схемы БД, переход сущность↔таблица, JPQL/HQL в `@Query` | JPQL/HQL — Spring Boot LS; сверка со схемой — своё (в плагине Database + Java), это главный пробел открытых инструментов | E22 |
| REST | HTTP-клиент на файлах `.http`/`.rest` (формат IntelliJ HTTP Client), переменные окружений, история, ответы | Формат — как у IntelliJ и httpyac (MIT), REST Client для VS Code (MIT); клиент — `reqwest` | E23 |
| gRPC | Подсветка и LSP для `.proto`, вызов методов по reflection или `.proto` | protols (MIT) или buf (Apache-2.0) как LSP; вызовы — `tonic`/`prost` (MIT/Apache-2.0), поведение — по grpcurl (MIT) | E23 |
| Redis | Подключения, дерево ключей, просмотр и правка значений по типам, консоль команд | `redis-rs` (BSD-3-Clause) | E24 |
| Kafka | Кластеры, топики, партиции, consumer groups и lag, чтение и отправка сообщений | `rdkafka` (MIT) поверх librdkafka (BSD-2-Clause); UI — по образцу Kafka UI (Apache-2.0) | E24 |
| RabbitMQ | Подключения, exchanges, очереди, bindings, публикация и чтение сообщений | `lapin` (MIT) для AMQP; HTTP API management-плагина | E24 |

Все плагины этой таблицы **процессные Rust-плагины** с обоснованием по разделу 8 v1.0: им нужны сеть и нативные драйверы, а у WASM-плагинов сети нет (раздел 3.3, вопрос 7). Языковые серверы (Spring Boot LS, protols, postgres-language-server) запускаются через Process Service, как JDT LS.

Ни один из этих плагинов не трогает L0/L1 (правило 2 раздела 30 v1.0): ядро получает только общие механизмы — DAP-клиент, конфигурации запуска, модели UI `Form` и `Table`.

## 6. Внешний вид и настройки

Ориентир — IntelliJ New UI: светлая и тёмная темы, спокойные цвета, компактные панели, иконки в стиле New UI. Иконки IntelliJ Community (Apache-2.0) можно брать с указанием источника. Сквозное требование ко всем этапам: всё, что видно пользователю, настраивается и красиво в обеих темах (правило 16).

### 6.1. Этап E17

- **Окно настроек** (`Ctrl+Alt+S`): дерево разделов, поиск по всем ключам, формы из JSON Schema ключей ядра и плагинов, показ слоя, из которого пришло значение (default, kit, пользователь, workspace, язык), сброс к умолчанию. TOML-файлы остаются источником правды.
- **Темы:** встроенные «Kumiko Light» и «Kumiko Dark» в духе New UI; редактор темы с живым предпросмотром, экспорт и импорт в TOML.
- **Шрифты и масштаб:** шрифт и размер редактора и интерфейса раздельно, лигатуры, межстрочный интервал, масштаб UI (90–200 %), режим «компактный / обычный».
- **Раскладка:** перетаскивание tool windows между боковыми и нижней областями, закрепление, скрытие, сохранение раскладки в профиль и в kit.
- **Клавиши:** раскладка IntelliJ по умолчанию (Windows/Linux), окно Keymap с поиском по команде и по сочетанию, показ конфликтов.
- **Редактор:** настраиваемые цвета подсветки по токенам, gutter, минимальная карта (по выбору), отображение пробелов, направляющие отступов.

### 6.2. Требования

- Все цвета и иконки — через токены темы (правило 11 v1.0); тема плагина может переопределить только свои токены.
- Смена темы, шрифта, масштаба и раскладки — без перезапуска.
- Контраст текста ≥ 4.5:1 в обеих встроенных темах.

### 6.3. Новые модели UI для плагинов (KPP 1.1)

| Модель | Что задаёт плагин | Что делает хост | Кто использует |
|---|---|---|---|
| Form | Поля по JSON Schema, значения | Рендер, валидация, отправка | Настройки, подключения к БД, Kafka, Redis |
| Table | Колонки, страницы строк (ленивая загрузка) | Виртуализация, сортировка, копирование, экспорт | Результаты SQL, сообщения Kafka, ключи Redis |
| DebugView | — (данные идут по DAP) | Окно Debug: стек, переменные, watch, консоль | Debugger |

Добавление методов — минорная версия KPP (1.1) по правилам заморозки v1 (`CHANGELOG-protocol.md`, правило 3 v1.0).

## 7. Релизы и ветки

### 7.1. Ветки

- `main` — только релизы. Каждый коммит на `main` соответствует тегу `vX.Y.Z` или исправлению релиза.
- `staging` — интеграционная ветка. Сюда сливаются этапы.
- `eNN-<имя>` — ветка этапа от `staging`, удаляется после слияния (включить «Automatically delete head branches» в настройках репозитория).

- GitHub Actions по тегу `v*`: сборка release на `windows-latest` и `ubuntu-latest`, артефакты в GitHub Release.
- Windows: `kumiko-X.Y.Z-windows-x86_64.zip` и `.msi` (cargo-wix / WiX Toolset). Linux: `kumiko-X.Y.Z-linux-x86_64.tar.gz` и `.AppImage` (appimagetool, MIT).
- Подписи кода нет. Контрольные суммы SHA-256 прикладываются.
- В архив входят: бинарь, встроенные плагины (`java`, `git`, `terminal`), ресурсы L3, kits `minimal` и `java`, лицензии зависимостей (`cargo about` или аналог). JDK и JDT LS не входят: они скачиваются при первом запуске.
- Чек-лист релиза: CI зелёный; бюджеты раздела 23 v1.0 замерены на обеих платформах; ручной сценарий установки с нуля пройден на обеих платформах; `CHANGELOG.md` обновлён.

## 8. Заимствование открытого кода

Разрешено решением владельца (раздел 2, п. 10) при таких условиях:

| Лицензия источника | Код | Идеи, форматы, UX |
|---|---|---|
| MIT, Apache-2.0, BSD, ISC, Zlib | Можно копировать с сохранением уведомления об авторстве и лицензии | Можно |
| MPL-2.0 (например, Helix) | Только целыми файлами, файлы остаются под MPL-2.0 | Можно |
| EPL (JDT LS, java-debug, Spring Tools) | Не копировать в репозиторий; использовать как отдельный процесс | Можно |
| GPL, AGPL, LGPL (например, Zed вне GPUI) | Запрещено | Можно, без переноса кода |
| Без лицензии или проприетарная (JPA Buddy, IntelliJ Ultimate) | Запрещено | Только общеизвестные приёмы |

- Перед копированием агент проверяет лицензию в репозитории источника (файл LICENSE, а не описание). При сомнении — не копировать.
- Скопированный код отмечается комментарием `// Adapted from <проект> (<лицензия>), <ссылка>`, уведомление добавляется в `THIRD_PARTY_NOTICES.md`.
- Новые Rust-зависимости — через cargo-deny (правило 4 v1.0).

Главные источники идей: IntelliJ Community (Apache-2.0) — модель run configurations, раскладка tool windows, keymap, HTTP Client; Lapce (Apache-2.0) — плагины и UI на Rust; Zed — UX GPUI-приложения (только идеи); vscode-java-debug (MIT) — UX отладки Java; DBeaver (Apache-2.0) — UX работы с БД.

## 12. Риски

| Риск | Последствие | Что делаем |
|---|---|---|
| Spring Boot LS и JDT LS вместе требуют много памяти | Обещание «лёгкая» под угрозой | Отдельный замер; Spring-плагин можно выключить; `-Xmx` настраивается; общий JVM для серверов — исследовать в E21 |
| JPA-проверки IDEA уровня Ultimate нет в открытом доступе | Объём своей работы в E22 | Начать со сверки сущностей и схемы; остальное — по запросу владельца |
| Мягкий перезапуск теряет состояние, которое трудно сериализовать | Пользователь теряет работу | Всё состояние сессии — в одном сериализуемом снимке; тест модульности 15 |
| GPUI 0.2 API нестабилен вне Zed | Сложнее перетаскивание панелей и новые виджеты | Обёртки в `kumiko-ui`; обновление GPUI — отдельными PR |
| Сервисы для тестов (PostgreSQL, Kafka, RabbitMQ, Redis) на Windows CI | Тесты E22–E24 только на Linux | Headless против контейнеров на Linux; на Windows — тесты с фейковыми серверами |
| Лицензии заимствованного кода | Юридический риск | Раздел 8, `THIRD_PARTY_NOTICES.md`, cargo-deny |
